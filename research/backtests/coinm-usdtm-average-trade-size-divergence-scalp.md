## 0. pandas/시간축 함정 점검

- UM/CM `open_time`(ms epoch int) → `pd.to_datetime(unit="ms")` → `.astype("datetime64[ns]")`로
  명시 통일. `prepare_symbol` 내부에서 `assert df.index.dtype == np.dtype("datetime64[ns]")`을
  UM/CM 원본, 병합 프레임, 1h 리샘플 프레임 전부에 실행해 확인.
- 1h confirm 매핑은 `Timedelta` 덧셈을 `.asi8 + delta_ns` 정수 연산으로만 처리하고(us 업캐스트

  관례로 "완결된 상위봉까지만" 사용 — 룩어헤드 방지(§10에서 절단 재실행으로 별도 확증).

## 3. 상관·전제 점검 — 사전 폐기조건 (a)(b)(d)

### 3-1. corr(z_ats_coinm, z_ats_usdtm) — 폐기조건(a): ≥0.7 이면 FAIL

`pandas.corr()`(pairwise) 사용:

```

pooled: 0.362
```

**전부 0.7 미만 — 폐기조건(a) 미트리거.** COIN-M ATS와 USDT-M ATS는 동일 정보의 재포장이
아니다(스펙의 설계 전제는 이 부분에서 지지됨).

### 3-2. 강추세 구간 자기잠식 — 폐기조건(b): 강추세에서 crossing 발생률이 유의하게 낮으면 FAIL

1h EMA20 4시간 슬로프 절대값 상위 20% 구간 vs 나머지 80% 구간의 gap crossing(롱+숏) 발생률:

```
BTC  강추세=0.0358 나머지=0.0504(비율 0.71) | ETH 0.0346/0.0434(0.80) | BNB 0.0422/0.0561(0.75)
SOL  0.0384/0.0534(0.72) | XRP 0.0421/0.0580(0.73) | DOGE 0.0411/0.0556(0.74) | ADA 0.0414/0.0544(0.76)
평균: 강추세=0.0394 나머지=0.0530
풀링 2비율 z-검정: z = −26.44 (n=1,120,896봉, 압도적으로 유의)
```

**7종목 전부 일관되게 강추세 구간에서 crossing 발생률이 약 25~29% 낮다 — 폐기조건(b) 명확히
트리거.** 스펙이 스스로 우려한 "가장 신호가 필요한 강추세 구간에서 게이트가 오히려 덜
발화한다"는 자기잠식 가설이 실측으로 확인된다.

### 3-3. COIN-M 15m count 결측/0 비율 — 폐기조건(d): >30% 면 해당 종목 제외

```
BTC 0.0175% | ETH 0.0181% | BNB 0.0181% | SOL 0.0187% | XRP 0.0187% | DOGE 0.0187% | ADA 0.0187%
```

**전 종목 0.02% 미만 — 폐기조건(d) 미트리거.** 스펙이 우려한 "알트 COIN-M count 희소성"은
15m 해상도에서도 실제로는 문제가 되지 않는다(7종목 전부 데이터 품질 우수).

### 3-4. 실측 승률 vs 손익분기 승률 — 폐기조건(c): 유의하게 낮으면 FAIL

```
평균 ATR%(전종목, 15m) = 0.5423%  (스펙 가정 0.30%보다 실측이 더 큼)
1R = ATR_mult(1.2) × ATR% = 0.6508%
cost_R = 0.14% / 0.6508% = 0.2151
재계산 손익분기 승률 wr* = (1+cost_R)/(1+RR) = (1.2151)/(2.5) = 48.61%
(스펙 원안 가정 손익분기 승률: 약 55.6%)

실측 승률: FULL 35.37% | OOS 36.00%
```

**실측 승률(35~36%)이 재계산 손익분기(48.6%)보다도 12~13%p 낮고, 스펙 원안(55.6%)과는
19~20%p 격차 — 폐기조건(c) 명확히 트리거.** n=44,204로 이 격차의 유의성은 압도적이다(뒤에서
t=−63로도 재확인).

**요약: 4개 사전 폐기조건 중 (b)·(c) 2개가 명확히 트리거됐다.** 스펙은 "이 중 하나라도 걸리면
FAIL"이라고 명시했으므로, 이미 이 시점에 폐기 대상이다. 사후에 이 임계값들을 다른 기준으로
바꾸지 않고 그대로 적용한다.

## 4. ⭐ 게이트 부가가치 — 동일 트리거 풀 내 gate=True/False 이분(R-배수)

리뷰어 지침에 따라 대조군 풀에 채택안이 포함되는 문제(base ⊆ pool)를 피하기 위해, **게이트 없는
"정렬 진입"(1h EMA20 위/아래 + 방향봉, 상태전이) 트리거 풀 전체**를 만들고, 그중 **같은 봉에
gap crossing도 동시에 발생했는지(gate=True)** 여부로 이분해 동일 SL/TP/시간청산 규칙으로
비교했다(같은 시뮬레이션 경로, 같은 청산 로직 — 진입 조건의 엄격도만 다름):

```
gate=True(채택 조건 충족)   FULL n=14,928  R_mean=−0.3173 t=−36.30 PF[R]=0.527 | OOS n=6,263  R_mean=−0.3086 t=−22.76 PF[R]=0.540
gate=False(게이트 없었으면) FULL n=159,635 R_mean=−0.2960 t=−116.07 PF[R]=0.528 | OOS n=71,029 R_mean=−0.2869 t=−74.17 PF[R]=0.545
```

**gate=True와 gate=False의 R_mean·PF[R]이 사실상 동일하다**(OOS PF[R] 0.540 vs 0.545, 차이는
오차범위 내). ATS gap crossing이라는 추가 조건은 **아무런 부가가치를 만들지 못한다** — 게이트를
걸든 안 걸든 결과가 통계적으로 구분되지 않으며, 둘 다 똑같이 크게 실패한다.

### 정보원 무력화 대조군 — COIN-M `volume`/`count` 블록셔플(30일 블록, 20회)

각 종목의 COIN-M `volume`·`count` 시계열을 30일(2,880봉) 블록 단위로 무작위 재배열해
`ats_coinm`을 재계산 → `gap` 재계산 → 신호·엔진 재실행(20회):

```
base(원본) OOS PF_net = 0.659 (n=18,908)
셔플 20회 OOS PF_net 범위: 0.628~0.740, 원본은 셔플 분포의 45번째 백분위(정확히 중앙)
```

**원본과 셔플 데이터가 통계적으로 구분되지 않는다** — COIN-M `volume`/`count`의 정확한 시간
정렬을 파괴해도 결과가 달라지지 않는다. 이는 §4(게이트 부가가치 없음)와 §7(무비용 진단에서도
gross 엣지 없음)을 세 번째 독립 경로로 재확인하는 것이다: **COIN-M ATS 신호는 실제 정보를
담고 있지 않다.**

⚠️ **한계(정직히 기록)**: 셔플 시 블록 경계(약 59개 지점)에서 90봉 롤링 윈도우가 서로 다른
블록의 데이터를 걸치며 일시적 미스매치를 만들어, 셔플군 신호빈도가 원본 대비 약 30~40% 더
많다(BTC 예시: 원본 7,592건 vs 셔플 예시 10,739건). 이 빈도 차이 때문에 PF 비교의 정밀도는
제한적이나(§상기 지시사항이 우려한 "빈도 불일치는 R-배수로" 원칙에 따라 첨언), 결과 분포가
워낙 넓게 겹치고(45번째 백분위) §4·§7의 독립적 증거와 방향이 일치해 정성적 결론(정보 없음)은
견고하다.

⚠️ **설계 결함 발견·기록**: 애초 계획했던 "일별 손익을 30일 블록으로 셔플"하는 방식은
**설계 결함**임을 스스로 발견했다 — 이미 실현된 일별 손익 합계를 블록 단위로 재배열해도
전체 부호·합계 구성(어느 날이 양수/음수인지)은 그대로 보존되므로 PF가 항상 원본과 동일하게
나오는 **트리비얼한(무정보) 검정**이었다. 대신 위와 같이 **신호를 만드는 원천 데이터(COIN-M
volume/count)**를 셔플하는 방식으로 교체해 재실행했다 — 이 프로젝트의 다른 라운드에서
관찰된 "신호원 셔플"과 동일한 계열의 올바른 설계다.

## 6. ⭐ 무비용 진단(fee=0, slippage=0) — gross 엣지 자체의 존부

```
IS   n=25,190  PF=0.986  t=−0.89(비유의)
OOS  n=18,812  PF=1.002  t=+0.10(비유의)
FULL n=44,002  PF=0.993  t=−0.52(비유의)
```

**수수료·슬리피지를 완전히 제거해도 PF는 정확히 1.0 근방이고 t는 비유의하다** — 이는 "작은
gross 엣지가 비용에 잠식됐다"는 이야기가 아니라, **원신호 자체가 애초에 동전 던지기(coin-flip)
수준의 기대값**이라는 뜻이다. §1의 net PF 0.48~0.76이라는 큰 실패폭은 전부 비용(수수료+슬리피지)
때문이며, 그 비용이 이토록 크게 작용하는 이유는 §2에서 확인한 **비정상적으로 높은 신호빈도**
(연 1,450~1,900건/종목) 때문이다 — 무정보 신호를 고빈도로 거래하면 비용만 누적된다는 전형적
패턴이다.

## 7. 방향반전 대조군

SL/TP·무효화·시간청산 전 분기가 `direction`(반전 여부까지 반영해 확정된 최종 방향 변수)만
참조하도록 구현(원신호 크로싱 플래그는 무효화 판정에서 방향에 따라 재매핑 — 코드로 확인,
`inval_col_for_dir = inval_long if direction==LONG else inval_short`).

```
정방향: FULL n=44,204 PF_net=0.660 t=−14.83
반전  : FULL n=44,773 PF_net=0.602 t=−17.35
zero_hold_frac: 정방향=11.58% 반전=12.92%
```

**반전도 정방향과 비슷하거나 더 나쁘다**(둘 다 크게 실패) — 방향 자체에 정보가 없다는 §6의
결론과 일치한다. `zero_hold_frac`이 정방향·반전 모두 11~13%로 비슷한 수준(0%나 90%+로
퇴화하지 않음)이라 반전 로직 버그(과거 여러 라운드에서 반복된 "원신호 플래그 재참조" 안티패턴)
의 징후는 없다. ⚠️ 다만 이 지표가 "0이 나오면 버그없음"을 자동 보장하는 것은 아니라는 과거
지적에 따라, 코드를 직접 읽어 무효화 판정이 `direction`(최종 확정 방향)만 참조함을 별도
확인했다(위 근거).
